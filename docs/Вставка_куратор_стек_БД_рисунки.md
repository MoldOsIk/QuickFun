## 1. Стек технологий (расширенное описание)

Клиентская часть реализована на языке Kotlin под управлением операционной системы Android. Для построения пользовательского интерфейса использован декларативный фреймворк Jetpack Compose и компоненты Material Design 3. Асинхронные операции (сетевые запросы, обновление состояния экранов) выполняются с применением корутин Kotlin (Coroutines); состояние экранов хранится во Flow/StateFlow, одноразовые события (сообщения пользователю) передаются через каналы в духе паттерна MVI. Зависимости между репозиториями и сценариями (use case) собраны в модуле инициализации приложения (AppModule). Сериализация данных ответов API выполняется средствами kotlinx.serialization.

Обмен с сервером осуществляется по протоколу HTTPS. Используется официальный клиент Supabase для Kotlin: подключены подсистемы Auth (аутентификация по электронной почте и паролю) и Postgrest (доступ к таблицам PostgreSQL через REST API). Низкоуровневая сетевая подсистема SDK опирается на библиотеку Ktor.

Серверная часть размещена в облачном проекте Supabase. В его составе: управляемая СУБД PostgreSQL, сервис аутентификации (учётные записи пользователей в схеме auth), автоматически формируемый слой PostgREST для таблиц схемы public, веб-консоль для администрирования (SQL Editor, просмотр таблиц, настройка Auth). Такой набор технологий позволяет сосредоточиться на модели данных и политиках безопасности без самостоятельной разработки отдельного сервера приложений на первом этапе проекта.

## 2. Проект в Supabase и прикладные таблицы (описание + место для скрина)

В веб-интерфейсе Supabase для проекта задаются уникальный URL облачного инстанса и ключи доступа. В клиентское приложение встраивается публичный (анонимный) ключ: он идентифицирует проект при обращении к API; фактические права на строки таблиц определяются политиками Row Level Security и сеансом пользователя после входа. Сервисный ключ, необходимый для административных операций в обход некоторых ограничений, в мобильное приложение не помещался и использовался только при настройке через консоль с рабочей места.

В разделе Table Editor отображаются таблицы схемы public: среди них users (профиль пользователя, связанный с идентификатором из auth.users), roles и user_roles (ролевая модель), categories (категории мест), locations (адрес и координаты), places (сущность «место»: название, описание, статус согласования, внешние ключи). Внешние ключи обеспечивают ссылочную целостность: например, место ссылается на локацию и категорию, связь пользователя с ролью — на справочник ролей.

## 3. Схема базы данных (ER-диаграмма)

Логическая структура базы данных отражает предметную область «каталог мест». Узлы: пользователь (public.users, ключ id совпадает с идентификатором в auth.users), роль (roles), связь многие-ко-многим между пользователями и ролями (user_roles). Справочник категорий (categories) связан с местами (places) в отношении «многие к одному». Каждое место может ссылаться на одну запись о локации (locations) с полями города, адреса, широты и долготы. У места задаются статус (например, одобрено для показа в общем списке), владелец (owner_id) и прочие атрибуты.

## 4. Аутентификация пользователя (описание + рисунки)

Регистрация и вход выполняются по электронной почте и паролю. При регистрации в сервисе Auth создаётся запись в auth.users; триггер на стороне PostgreSQL копирует идентификатор пользователя в public.users и подставляет имя из метаданных профиля или из локальной части адреса почты. После успешного входа клиент получает сеанс с JSON Web Token (JWT); при запросах к таблицам public токен передаётся автоматически, что позволяет в политиках безопасности использовать функцию auth.uid() для идентификации текущего пользователя.

## 5. Триггеры и политики безопасности (описание + скрин SQL)

Для автоматического создания записи в public.users при появлении нового пользователя в auth.users используется функция-триггер (на языке PL/pgSQL), выполняемая с правами security definer. Политики Row Level Security на таблицах places, locations и categories задают, кто может читать и изменять строки: в частности, выборка мест для широкого круга пользователей ограничена записями со статусом одобрения либо расширена для учётной записи администратора; вставка и обновление мест и локаций разрешены при выполнении условия роли администратора через функцию is_admin().

Фрагмент скрипта создания триггера или политик RLS целесообразно показать на скриншоте из SQL Editor (Рисунок 6), без отображения секретных ключей и персональных данных.
