## 4.1. Общая характеристика разрабатываемой системы

Разрабатываемая система QuickFun предназначена для работы с каталогом мест (например, организаций досуга) на платформе Android. Пользователь просматривает записи, прошедшие согласование (статус в базе данных), ведёт профиль после входа в учётную запись. Учётной записи с ролью администратора доступны добавление новых мест и изменение существующих записей, включая привязку к географической локации (город, адрес, широта и долгота).

Архитектура решения двухзвенная: клиентское приложение на языке Kotlin выполняется на мобильном устройстве; хранение и обработка данных выполняются в облачном проекте Supabase на базе СУБД PostgreSQL. Обмен по протоколу HTTPS; для доступа к таблицам используется REST-слой PostgREST. Локальная база данных на смартфоне не развёртывается — достоверное состояние данных обеспечивается на сервере, на клиенте сохраняется сеанс аутентификации средствами SDK.

Бизнес-логика отделена от интерфейса: экраны обращаются к сценариям (use case), те — к репозиториям, реализующим вызовы API. Такое разделение соответствует принципам Clean Architecture и упрощает сопровождение кода.

## 4.2. Серверная часть: платформа Supabase, проект, схема базы данных и политики безопасности

### 4.2.1. Проект Supabase и подключение клиента

Платформа Supabase объединяет управляемый экземпляр PostgreSQL, сервис аутентификации пользователей (схема auth), автоматически формируемый REST-доступ к таблицам схемы public через PostgREST и веб-консоль (настройка проекта, Table Editor, SQL Editor, раздел Authentication).

В настройках проекта задаются URL облачного инстанса и ключи. В мобильное приложение встраивается публичный (анонимный) ключ: он идентифицирует проект при обращении к API. Реальные права на строки таблиц определяются не «открытостью» ключа, а политиками Row Level Security и наличием валидного JWT после входа пользователя. Сервисный ключ, применяемый для администрирования и скриптов в обход части ограничений, в клиентское приложение не помещался и использовался только в веб-консоли при настройке с рабочей станции в соответствии с требованиями к работе в ЛВС.

### 4.2.2. Логическая схема базы данных

Предметная область — каталог мест. В схеме public используются, в частности, следующие сущности:

- users — профиль пользователя; поле id совпадает с идентификатором записи в auth.users;
- roles — справочник ролей (например, user, admin);
- user_roles — связь «пользователь — роль» (многие-ко-многим);
- categories — категории мест;
- locations — адрес, город, географические координаты;
- places — место: название, описание, статус согласования, внешние ключи на категорию, локацию, идентификатор владельца (owner_id).

Внешние ключи поддерживают ссылочную целостность: место ссылается на категорию и локацию; роли пользователя — на справочник roles. Связи между таблицами рекомендуется изобразить на ER-диаграмме (Рисунок 4.3), подготовленной в pgAdmin, DBeaver, draw.io или экспортированной из инструментов моделирования.

### 4.2.3. Аутентификация и синхронизация учётных записей

Регистрация и вход выполняются по электронной почте и паролю. Новая учётная запись создаётся в auth.users. Для автоматического появления строки в public.users применяется функция-триггер на языке PL/pgSQL (например, handle_new_user): при вставке в auth.users добавляется запись в public.users с тем же id; имя подставляется из метаданных профиля (full_name, name) или из локальной части адреса email. Роль по умолчанию назначается отдельным скриптом через таблицы user_roles и roles.

После успешного входа клиент получает сеанс с JSON Web Token; при запросах к таблицам public токен передаётся автоматически, в политиках безопасности доступна функция auth.uid() — идентификатор текущего пользователя.

### 4.2.4. Политики Row Level Security и обращение к API

Для таблиц places, locations и categories включён Row Level Security. Реализована функция is_admin() с атрибутом security definer: она проверяет наличие роли admin у текущего пользователя в user_roles и используется в политиках SELECT, INSERT, UPDATE. Типичная логика: обычному пользователю доступно чтение мест со статусом одобрения; администратору — расширенный доступ на чтение и изменение в соответствии с политиками.

Запросы к данным формируются через SDK к PostgREST. Для списка мест выполняется выборка из places с фильтром по статусу approved и вложенным развёртыванием связей к categories и locations. При создании места администратором соблюдается порядок операций: сначала вставка в locations с получением id, затем вставка в places с явным указанием статуса (например, approved), иначе значение по умолчанию в БД могло бы оставить запись невидимой для общего каталога. При редактировании обновляются сначала поля локации, затем места.

## 4.3. Архитектура клиентского приложения и технологический стек

Клиентская часть реализована на языке Kotlin под управлением ОС Android. Пользовательский интерфейс построен на Jetpack Compose с использованием компонентов Material Design 3. Асинхронные операции (сетевые запросы, обновление состояния экранов) выполняются с применением корутин Kotlin (Coroutines); состояние экранов хранится во Flow/StateFlow, одноразовые события (сообщения пользователю) передаются в подходе, близком к паттерну MVI. Зависимости между репозиториями и сценариями (use case) собраны в модуле инициализации (AppModule). Сериализация ответов API выполняется средствами kotlinx.serialization.

Обмен с сервером — по HTTPS. Используется официальный клиент Supabase для Kotlin с подключёнными модулями Auth и Postgrest; сетевая подсистема SDK опирается на библиотеку Ktor. Перед обращением к таблицам в репозиториях вызывается загрузка сеанса из хранилища (loadFromStorage), чтобы JWT учитывался политиками RLS.

Слой domain содержит модели предметной области, интерфейсы репозиториев и use case (вход, регистрация, список мест, создание и обновление места, профиль, сохранение имени). Слой data реализует репозитории и DTO; слой ui — экраны и ViewModel. Точка входа MainActivity переключает отображение между экраном авторизации и основным содержимым (каталог, профиль) в зависимости от состояния сеанса (в т.ч. с использованием AnimatedContent).

## 4.4. Реализация пользовательских сценариев и функций каталога

До входа пользователь видит форму авторизации и может перейти к регистрации; обрабатываются состояния загрузки, ошибки сети, при необходимости — ожидание подтверждения электронной почты (в зависимости от настроек проекта Supabase).

После входа загружается список мест с отбором по одобренным записям; на экране профиля отображаются адрес электронной почты, имя из public.users и перечень ролей из связки user_roles и roles. Имя можно изменить и сохранить через операцию upsert в таблице users.

Пользователю с ролью администратора доступны диалоги создания места (название, описание, город, адрес, широта и долгота, при необходимости категория) и редактирования по выбору элемента списка. Если связь с локацией отсутствует, редактирование блокируется с пояснением. После сохранения данные списка обновляются в той же корутине.

## 4.5. Тестирование, отладка и обеспечение безопасности данных

Проверка выполнялась на эмуляторе Android Studio и (или) на физическом устройстве. Тестировались успешный и неуспешный вход, восстановление сеанса после перезапуска приложения, корректность формирования JSON при вставке и обновлении, поведение при отсутствии сети, соответствие отображаемого списка политике (для обычного пользователя — записи со статусом одобрения). В SQL Editor консоли Supabase выполнялись скрипты создания триггеров и политик; при проверке RLS сравнивались ответы API для учётной записи с ролью администратора и без неё.

Секреты сервисной роли в приложение не включались. Политики безопасности реализуются на сервере; клиент не содержит обхода механизма RLS.
